## What actually solves this correctly (already investigated, don't re-derive)

The `codex app-server` protocol (the same JSON-RPC-over-stdio protocol `packages/happy-cli/src/codex/codexAppServerClient.ts` already speaks to run Codex threads) has a real, documented RPC: method name **`model/list`**. Confirmed by running `codex app-server generate-json-schema --out <dir>` and reading the generated `v2/ModelListParams.json` and `v2/ModelListResponse.json`. Do not re-derive this from scratch, though you're welcome to regenerate the schema yourself to double check; the shape below is already verified correct.

- Request params (`ModelListParams`), all optional: `{ cursor?: string | null, includeHidden?: boolean | null, limit?: number | null }`. Call with `{}` (no cursor, first page, default limit, hidden models excluded). This mirrors what a normal model picker wants.
- Response (`ModelListResponse`): `{ data: Model[], nextCursor: string | null }`. Handle pagination minimally: if `nextCursor` is non-null after your first call, either follow it once or twice more to gather a complete first page, or document in your summary why you chose not to. This is a picker list, not a searchable catalog, so a bounded number of pages is fine. Do not build unbounded pagination.
- Each `Model` has (relevant fields only, see the full schema in your own regenerated JSON for the rest): `id: string`, `model: string`, `displayName: string`, `description: string`, `hidden: boolean`, `isDefault: boolean`, `defaultReasoningEffort: string`, `supportedReasoningEfforts: { reasoningEffort: string, description: string }[]`, `upgrade?: string | null`, `upgradeInfo?: { model: string, migrationMarkdown?: string|null, modelLink?: string|null, retirementAt?: number|null, upgradeCopy?: string|null } | null`.

## Design constraint: this must NOT slow down daemon startup or spam the Codex process

Identical constraints to the Claude build, because the underlying cost is the same shape (spawning a real CLI subprocess and doing a handshake):

1. Run this probe asynchronously, off the critical path. Daemon startup and session creation must not wait on it.
2. Cache the result with a reasonable TTL. Mirror whatever choice `packages/happy-cli/src/utils/detectClaudeModels.ts` made (re-probe once per daemon process lifetime) and justify in your summary if you diverge.
3. Fail gracefully. If `codex` is not installed, the app-server subprocess fails to spawn, the RPC errors, or the response fails to parse, the field must simply be absent or undefined. Never throw, never block, never crash the daemon.
4. Do not spawn more than one probe process concurrently, and do not leave an orphaned `codex app-server` child process if the daemon shuts down mid-probe (this is why reusing `withCodexAppServerClient`'s try/finally disconnect matters).
