# Codex Independent Review: OpenHands Harness (510d7714, 8130de71, 0c223dc2)

## Verdict: REWRITE

## Findings

1. `packages/happy-cli/src/daemon/run.ts:461` — **blocker** — The tmux path does not actually remove `DEEPINFRA_API_KEY` from the spawned OpenHands process. `childAmbientEnvironment` correctly omits it from the `-e` values at lines 352–354 and 473–477, but tmux windows inherit their server environment when a key is omitted. The existing sanitizer invoked at line 461 only unsets `SESSION_SCOPED_ENV_KEYS`; `DEEPINFRA_API_KEY` is not one of them. This is also documented by `packages/happy-cli/src/utils/tmux.ts:798-800`. Therefore, if the selected tmux server was started with the host key, the new window retains both the raw `DEEPINFRA_API_KEY` name and value alongside the intended `LLM_API_KEY`. Suggested fix: explicitly unset `DEEPINFRA_API_KEY` in the command executed for either OpenHands preset (or extend the tmux sanitizer with a per-launch deny-list), and add a tmux-path test whose server environment contains the host key.

2. `packages/happy-app/sources/utils/newSessionAgentSelection.ts:29` (reached through `packages/happy-app/sources/sync/machineChoices.ts:192`) — **major** — Both OpenHands presets are advertised from the shared `cliAvailability.openhands` flag, but the final launch-time resolver looks up `availability[selectedAgent]`. For `openhands_local` and `openhands_deepinfra`, those properties are undefined even when `availability.openhands === true`. Consequently `resolveChoiceAgent` first accepts the preset in `machineChoiceAgentAvailable`, then replaces it with the first ordinary available harness (normally Claude) in `resolveMachineAgent`. The Home composer and dedicated New Session page both use this resolver immediately before spawning, so the selectable OpenHands rows cannot reliably start OpenHands. Suggested fix: make `resolveMachineAgent` use the same shared-key availability mapping as `isHarnessAvailable`/`machineChoiceAgentAvailable`, and add launch-resolution tests for each preset with `{ openhands: true, claude: true }`.

3. `packages/happy-cli/src/agent/acp/runAcp.ts:439-477` — **major** — An OpenHands launch is recorded as generic flavor `acp`, not `openhands_local` or `openhands_deepinfra`; `resolveSessionFlavor` maps every ACP agent other than Gemini/OpenCode to `acp`. It also ignores the daemon-provided `HAPPY_FORKED_FROM_SESSION_ID`, so an OpenHands second-opinion child loses its `parentSessionId`. This breaks the first-class harness identity after creation: the OpenHands-specific model/permission catalogs are selected only for the two OpenHands flavors, and the handoff menu does not recognize a current `acp` session as OpenHands, so it can offer OpenHands as another target again. The handoff does not pass the source session's auth token or provider session ID, but its requested lineage and target identity are not persisted. Suggested fix: carry an explicit Happy session flavor and parent/fork metadata through the ACP runner for these two presets, then test both created metadata and the subsequent picker/handoff behavior.

4. `packages/happy-cli/src/daemon/run.ts:347-379` — **major** — The opaque DeepInfra API-key value is merged into `extraEnv` before `expandEnvironmentVariables` runs. If an otherwise valid key contains `${...}`, the generic profile-expansion routine rewrites it using the daemon environment or rejects it as unresolved. This is unsafe for a credential that must be passed byte-for-byte; it can also substitute an unrelated daemon value into `LLM_API_KEY`. The fixed model/base-url values are not currently affected because they contain no template expression. Suggested fix: expand only user/profile-supplied environment values before merging the OpenHands launch plan, or exempt launch-plan credential values from expansion; add a regression test with a literal `${NAME}` sequence in the host key.

## Review coverage

Reviewed all 30 files in the scoped diff and traced the launch flow from picker availability through `machineSpawnNewSession`, daemon environment construction, ACP invocation, and ACP session metadata. I also traced the second-opinion flow: it sends a capped plain-text transcript only after a fresh target session is created; it does not forward the source session's token, provider conversation identifier, or environment variables. The direct non-tmux spawn strips the host `DEEPINFRA_API_KEY` and maps its value only to `LLM_API_KEY`; the tmux inheritance path above invalidates that guarantee.
