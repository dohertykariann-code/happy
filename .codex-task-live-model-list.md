## Problem being fixed

`packages/happy-app/sources/components/modelModeOptions.ts` function `getClaudeModelModes()` (around line 169) is a hand-maintained, hardcoded array of Claude model rows (Fable 5.1, Fable 5, Opus 5, Opus 5 [1M], Sonnet 5). ## What actually solves this correctly (already investigated, don't re-derive)

The `@anthropic-ai/claude-agent-sdk` package (pinned at `^0.3.259` in `packages/happy-cli/package.json`) that `happy-cli` already depends on exposes exactly the right primitive: a `Query` object (the thing returned when you start a Claude session via the SDK) has an async method `supportedModels(): Promise<ModelInfo[]>` (see `sdk.d.ts` around line 2738, type `ModelInfo` around line 1266). This returns the list of models the actual installed CLI can currently launch: value (model id to pass to `--model`), resolvedModel (canonical wire id), displayName, description, supportsEffort, supportedEffortLevels, supportsAdaptiveThinking, supportsFastMode. This is strictly better than hitting Anthropic's public `/v1/models` endpoint, because it is already scoped to what this specific CLI version supports. No separate verification step is needed.

`SDKControlInitializeResponse` (the response from the SDK's `initialize` control request, returned by `Query.initializationResult()`) also carries a `models: ModelInfo[]` field, populated as soon as a session starts. This may be cheaper to obtain than waiting on `supportedModels()` if starting even a minimal query already triggers `initialize`. Investigate both call shapes yourself against the installed SDK's actual runtime behavior, not just the type declarations, and use whichever is more reliable and cheaper. Do not guess API behavior beyond what the `.d.ts` files document. If something is ambiguous, spin up a tiny throwaway script that imports the SDK and logs the real return value, then delete the script.

## How capability info already flows from CLI to app (follow this exact pattern)

`packages/happy-cli/src/utils/detectCLI.ts` exports `detectCLIAvailability(): CLIAvailability`, a synchronous, cheap set of `command -v` checks (or `Get-Command` on Windows) run at daemon startup. The result is attached as `cliAvailability` on `MachineMetadata`, published via `packages/happy-cli/src/daemon/run.ts:57` (`cliAvailability: detectCLIAvailability()`), and the schema lives in `packages/happy-cli/src/api/types.ts` around line 143 (`MachineMetadataSchema.cliAvailability`). On the app side, this metadata eventually reaches `packages/happy-app/sources/sync/machineChoices.ts` and is read by `packages/happy-app/sources/components/modelModeOptions.ts`'s `getClaudeModelModes()` (today a hardcoded function with no parameters) and by whatever calls it. ## Design constraint: this must NOT slow down daemon startup or spam the CLI process

Unlike `detectCLIAvailability()` (cheap, synchronous, safe to run every daemon boot), getting `supportedModels()` requires actually starting a Claude Agent SDK query, which spawns a real CLI process and does a real `initialize` handshake. This is not cheap and must not block or slow daemon startup or session creation. Design requirements:

1. Run this probe asynchronously, off the critical path. Daemon startup and session creation must not wait on it.
2. Cache the result with a reasonable TTL (for example, re-probe once per daemon process lifetime, or once per some number of hours; pick something sensible and justify it in your summary; this does not need to be real-time-fresh, CLI installs do not change every few minutes).
3. Fail gracefully. If the probe errors, times out, or the installed SDK or CLI version does not support `supportedModels()` or `initializationResult()` at all, the field must simply be absent or undefined. Never throw, never block, never crash the daemon.
4. Do not spawn more than one probe process concurrently, and do not leave orphaned child processes if the daemon shuts down mid-probe.
